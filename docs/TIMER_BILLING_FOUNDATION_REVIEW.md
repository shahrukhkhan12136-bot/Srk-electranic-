# Timer Billing Foundation — Pre-RPC Review

Date: 2026-11-11  
Branch: `feature/production-push-notifications`  
Scope: Static review only. No Supabase database was modified and no deployment was performed.

## Reviewed source

`supabase/migrations/202611110001_timer_billing_materials_foundation.sql`

The migration is an additive schema foundation. It deliberately does not create the customer/electrician/Admin RPCs or switch the application to the new workflow. It must not be treated as production-ready merely because it is committed.

## Findings to resolve before writing or applying RPCs

1. **Decision immutability is not enforced yet.** The timer decision table is described as an append-only ledger, but the current schema allows privileged service-role updates/deletes. Implement an explicit event/decision model and database guards so approved decisions and effective timestamps cannot be rewritten. Pending-to-final transition must be a single controlled operation.
2. **Final bills and material evidence need immutability.** Add database-side protections against changing/deleting generated bills, bill calculations, material line items, and approval evidence after issue/approval. Corrections should create a new version/revision with an audit trail, not overwrite history.
3. **RPC authorization must be based on trusted identity.** Every exposed RPC must derive actor identity from `auth.uid()`, validate customer ownership or assigned electrician linkage (`user_id` and `auth_user_id` where applicable), and use the existing Admin authorization helper. Never accept actor IDs, roles, timestamps, elapsed time, rates, or amounts as trusted client inputs.
4. **SECURITY DEFINER must be exceptional and hardened.** Prefer invoker functions. If definer rights are unavoidable, set a fixed empty/known `search_path`, schema-qualify every object, revoke default EXECUTE from PUBLIC/anon/authenticated, grant only the required role, and perform explicit `auth.uid()`/role/ownership checks inside the function.
5. **Timer transitions require row locking and idempotency.** Lock the booking row before validating state; reject out-of-order actions; make repeated requests with the same idempotency key return the original result; prevent a second pending or approved start/stop from racing.
6. **Use server timestamps only.** Effective start/stop timestamps must be generated by the database at the exact approval transaction. A pending stop request must not stop billing. The bill must be generated only after customer approval is committed.
7. **Decimal arithmetic and elapsed-time precision need tests.** The schema stores numeric rates and rounded money, but the RPC must use exact decimal arithmetic and the approved whole-minute ceiling rule, then round the final labour amount once to ₹0.01 using half-up. Define whether timestamp precision is whole-second or microsecond and ensure elapsed seconds and billed minutes cannot disagree at boundaries.
8. **Category/rate snapshot must be validated at booking creation.** Use a fixed server-owned mapping (helper ₹899/8h, ordinary ₹1,199/8h, skilled ₹1,599/8h, master ₹1,999/8h). Do not accept arbitrary client rate values or infer category from free-text skills.
9. **Materials remain a separate approval/payment domain.** Validate item totals server-side, require itemized descriptions/quantities/unit prices, retain receipt evidence when electrician supplies materials, and do not merge materials into labour or labour commission.
10. **Cancellation fee is an Admin decision, not a client parameter.** The ₹99 fee can apply only when arrival evidence exists, the customer requested cancellation, and Admin explicitly approves. Non-arrival means ₹0. Other cancellation cases must not be guessed or charged.
11. **Migration idempotency needs a clean replay test.** Several `ADD CONSTRAINT` statements are not guarded by catalog checks, so rerunning the file after partial application may fail. Verify clean migration replay in an isolated database and decide whether the migration runner guarantees atomic application.
12. **Circular final-bill references need lifecycle verification.** `service_bookings.final_bill_id` references `srk_final_bills.id`, while each bill references its booking. This is valid as a deferred lifecycle design only if the RPC inserts the bill and links the booking in one transaction; test rollback and uniqueness behavior.
13. **Historical compatibility remains mandatory.** Do not drop old quote/payment columns, legacy records, RPCs, or triggers until all current readers/writers, finance reports, and historical receipts are mapped and migrated.

## Required test matrix before any database application

- Fresh database migration replay and rollback behavior.
- Customer vs unrelated customer vs assigned electrician vs unassigned electrician vs Admin.
- Start request/approve/reject, duplicate key, concurrent approval, and invalid state transitions.
- Stop request pending (timer still runs), approve stop, reject stop, duplicate stop, and concurrent requests.
- Exact boundary durations: 0s, 1s, 59s, 60s, 61s, 119s, 120s, and 8h.
- Four approved rates; final half-up rounding to paise; no minimum charge.
- Attempts to spoof rate, actor, timestamps, elapsed seconds, minutes, and amount.
- Material item arithmetic, separate approval, rejection, and post-approval mutation attempts.
- Cancellation with/without arrival evidence, requester role, Admin approval/rejection, and fee correctness.
- Existing bookings and historic quote/payment/commission reports remain readable.
