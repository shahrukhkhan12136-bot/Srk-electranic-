# Unified Timer, Bill, Materials and Payment Contract — Design Gate

Date: 2026-11-11  
Branch: `feature/production-push-notifications`  
Status: design gate only; no schema or runtime changes.

## Purpose

Unify the customer-approved timer flow, labour-only final bill, separately approved materials, cancellation decision, and Cash/Online payment into one consistent state model. This document records design decisions that must be settled before writing RPCs or changing API/UI callers.

## Non-negotiable invariants

1. The browser never supplies authoritative user/profile identity, actor role, arrival/start/stop time, elapsed duration, hourly rate, billable minutes, labour amount, material line total, final payable total, commission, payout, or payment status.
2. All state-changing actions are authenticated, ownership-checked, booking-row locked, idempotent and audited.
3. An electrician can act only when the booking is assigned to that exact active, approved profile AND an accepted offer exists, unless a separately audited Admin assignment path is explicitly implemented.
4. Customer approval is required for both timer start and timer stop. A pending stop request does not stop billing.
5. Final bill is generated in the same transaction as customer stop approval, using one server timestamp and the booking's saved category/rate snapshot.
6. Labour and materials are distinct. Material approval is a separate customer decision. Customer-supplied items are never charged as electrician-supplied materials.
7. No payment choice, payment order, advance, or checkout at booking creation or while timer is running.
8. Online and Cash payment are enabled only after stop approval, final bill creation, and customer material decision for all proposed material revisions.
9. Payment amount is computed on the server from the approved bill plus approved electrician-supplied material revisions only.
10. A completed/paid transition, receipt, commission and payout are not duplicated by request retries or webhook replay.

## Canonical lifecycle

### Booking and assignment
- Customer creates a booking with validated category code, location and service details.
- Server maps category code to the approved rate and snapshots category code, label and hourly rate. The browser cannot submit the rate.
- Booking has no payment method and no final amount.
- Offer acceptance atomically assigns the electrician and marks exactly one offer accepted; competing offers are closed.
- A timer RPC requires assignment plus accepted-offer evidence. Admin assignment, if retained, must write a separate immutable assignment audit record and satisfy equivalent profile checks.

### Arrival and timer
- Arrival is a separate timestamped event, recorded by the assigned electrician and auditable. Arrival is not billable.
- Start request requires recorded arrival and creates one pending decision.
- Customer approves/rejects the exact pending decision. Approval timestamp is generated by the database.
- Stop request is accepted only while running; timer remains running while pending.
- Customer rejection returns the timer to running.
- Customer approval stops the timer and creates the one initial labour bill atomically.
- No second start or stop cycle is allowed for the same initial work session. A legitimate additional visit/work session requires a separately specified amendment/session model, not reuse of the original bill.

### Labour calculation
- elapsed seconds = CEIL(server stop timestamp - server start timestamp), clamped at zero.
- billable minutes = 0 for zero elapsed seconds; otherwise CEIL(elapsed seconds / 60).
- labour = hourly snapshot × billable minutes / 60.
- use full numeric precision and round only the final labour amount to ₹0.01 using PostgreSQL numeric round (half away from zero for positive amounts).
- no minimum charge.
- Persist calculation version, timestamps, elapsed seconds, billable minutes, hourly snapshot and labour amount for audit.

### Materials
- Material items belong to a specific material revision, not merely to the bill.
- Each revision is a complete proposed set of electrician-supplied material lines and has a unique revision number per bill.
- Each line has validated description, quantity, unit price, computed line total, supplier, receipt evidence/reference and creator.
- Customer approves/rejects one exact revision. A later change creates a new revision and requires new approval.
- Approved revisions and their lines/decision evidence are immutable.
- Customer-supplied items may be recorded for transparency but contribute zero to electrician payable and customer materials payable.
- Rejected or pending revisions contribute zero to payable.
- The final payable is labour plus only the latest customer-approved electrician-supplied material revision (or approved revision total under an explicitly defined cumulative policy). The product must choose one policy before implementation; default recommendation is a full replacement revision, not cumulative addition.

### Payment
- Payment eligibility is derived from: timer stopped, final bill exists, and no material revision is pending customer decision.
- Cash: customer pays electrician directly; only the assigned electrician can confirm receipt. Store actor, timestamp, bill revision and exact paid amount. Admin can audit and resolve disputes; Admin must not silently fabricate electrician confirmation.
- Online: order creation binds to booking ID, final bill ID/version, approved material revision ID (or explicit zero-material marker), exact amount in paise and currency.
- Reusable order is valid only for the exact same bill/version/material revision/amount.
- Payment verification and webhook both call the same transactional reconciliation routine. Provider signature/lookup validation occurs before the database call; the database then locks and validates order binding, bill/revision state, amount, currency and payment identity.
- Persist provider webhook event ID uniquely, payload digest, received time, processing status, outcome and retry metadata. A repeated event ID is a no-op returning the prior outcome.
- Same payment ID retry is success; different payment ID after settlement is conflict and Admin review.
- Booking completion, receipt, commission and payout side effects must be idempotent and must not include material charges in labour commission.

## Required data-model corrections before RPC implementation

The current foundation migration is a partial skeleton and is not sufficient as-is:

1. **One pending decision:** add a partial unique index preventing more than one pending start request and more than one pending stop request per booking. RPC state checks still remain mandatory.
2. **Idempotency scope:** define key length/format, actor binding, action binding and retention. A repeated key from a different actor must not reveal another user's decision payload.
3. **Material revision ownership:** add a material-revision parent table (bill ID, revision, status, creator, timestamps) and link material lines to revision ID. Current material lines link only to bill, so approvals cannot prove which exact line set was approved.
4. **Material approval uniqueness:** unique (bill_id, revision) is useful, but revision rows must exist and be immutable after decision; approval must reference the exact revision ID.
5. **Final bill correction policy:** current unique booking_id on final bills permits only one bill and cannot support a separately audited correction. Preserve the initial immutable labour bill and model adjustments as append-only adjustment records with reason, amount delta, Admin actor, and explicit customer approval where payable increases. Do not overwrite the original.
6. **Payable snapshot:** add a persisted immutable payment-eligibility/payable snapshot or order binding that records exact bill version, approved material revision, amount paise, currency and calculation version.
7. **Webhook ledger:** add a durable unique provider event ledger and a provider payment/order mapping with uniqueness constraints.
8. **Cash evidence:** add an immutable cash-receipt record bound to exact payable snapshot; do not rely on a generic booking status or editable amount.
9. **Arrival evidence:** use a dedicated arrival event record or ensure the booking timestamp can only be set once by the authorized RPC and cannot be overwritten by generic Admin/browser updates.
10. **Protected booking columns:** implement database guards preventing generic client/API update paths from changing category/rate snapshots, arrival, timer fields, bill links, payment fields and payable state. RPCs must use narrow, intentional mutation paths.
11. **Audit:** generic booking audit trigger omits new timer/bill details; add dedicated append-only audit events with actor, action, entity, request key, before/after state hash or safe structured metadata, and server timestamp.
12. **Scoped reads:** provide customer, assigned electrician and Admin read functions for timer decisions, bill, materials and payment evidence. Do not grant broad table SELECT or expose service-role tables to the browser.
13. **RPC schema exposure:** prefer a non-exposed schema for privileged functions if supported by the project API configuration; otherwise public functions must explicitly revoke PUBLIC/anon and grant only minimum authenticated roles, with internal auth checks and fully qualified references.

## Important implementation hazards already observed

- The shared TEST project is not a complete schema replica; do not apply the foundation migration there blindly.
- Existing production legacy work-status RPC is executable by authenticated users and bypasses customer timer approval. Retire only after every caller is migrated and verified.
- Existing booking creation accepts a payment method and client quote.
- Existing order creation, verification and webhook all use legacy quote fields and direct privileged booking writes.
- Customer, electrician and Admin dashboards still contain legacy quote/payment UI and direct Admin booking edits.
- Existing service-booking triggers perform legacy quote/payout side effects. Timer RPCs must avoid legacy trigger columns until the complete cutover, and final payment/payout must be explicitly redesigned and tested.
- Foundation migration's service_role table grants are broad. They are not a substitute for immutability controls.
- Circular booking/final-bill FK has only been exercised in a minimal synthetic harness, not a Production-equivalent schema.

## RPC surface to implement only after schema gate

Minimum proposed operations:
- customer booking creation (rate snapshot server-side)
- electrician arrival record
- electrician timer start request
- customer timer decision (approve/reject exact request)
- electrician timer stop request
- customer stop decision + atomic labour bill generation
- electrician material revision submission
- customer material revision decision
- customer/electrician/Admin scoped timer/bill/material reads
- customer cancellation request
- Admin cancellation decision
- payable snapshot creation/read
- Razorpay order claim/bind
- payment reconciliation (shared by verify endpoint and webhook)
- electrician cash receipt confirmation
- Admin audited payment dispute/adjustment operations

Every mutation RPC must define its exact actor, row locks, allowed prior state, idempotency semantics, uniqueness constraints, audit event and expected error codes before implementation.

## Release gates

### Gate A — design complete
- Choose material revision policy (replacement vs cumulative).
- Define whether multiple visits/work sessions are supported.
- Define correction/adjustment and refund rules for already-approved/paid bills.
- Define Cash receipt dispute and Admin correction rules.
- Finalize category/rate snapshot and all payable formulas.

### Gate B — isolated schema and RPC verification
- Build a disposable PostgreSQL environment from complete authoritative schema/migrations, not the partial shared TEST project.
- Apply migration cleanly and twice; test rollback and partial failure.
- Test all roles, ownership, accepted-offer linkage, profile ambiguity, replay, concurrency and trigger side effects.
- Test bill/material/payment reconciliation and webhook event idempotency.

### Gate C — coordinated application cutover
- Update customer, electrician, Admin and all Netlify handlers together.
- Remove all old quote/payment callers.
- Confirm no active code path can invoke legacy work status or directly mutate protected fields.
- Run browser end-to-end tests and payment provider Test Mode tests.

### Gate D — separately approved release
- Obtain explicit approval before shared TEST or Production database writes.
- Obtain explicit approval before any production deployment.
- Do not incur paid provider/service costs without approval.

## Current state

This document is a design gate only. It does not mean the timer, bill, materials or payment system has been implemented. No database was changed and no deployment occurred.
